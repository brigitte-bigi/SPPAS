User manual

Description

The Dashboard is the page SPPAS opens when it starts. It is the hall of the software: it shows what can be launched, tells which workspace is in use, and gathers the ways out -- towards the other applications, towards the pages of information, and towards the web site. It carries no work of its own: nothing is annotated, converted or analysed here.

The page is served under the name index.html. Closing its tab does not stop SPPAS; leaving the session is an explicit action, taken from the menu.

What the page shows

The applications

Each application of SPPAS is shown as a card: a picture, its name, a short description, and the button launching it. The first card, named Desktop, launches the classic interface -- the one written with wxPython -- and not SPPAS as a whole: SPPAS 5 is the product, that interface is one of its components.

A card is disabled when the feature it needs is not installed. The Desktop card keeps its Launch button disabled while that interface is already running, and stays otherwise unchanged.

The current workspace

Above the cards, the name of the workspace in use is displayed, with the path of its file as a tooltip. It is shown for reading only: the workspace is chosen elsewhere. The name is refreshed on its own, without reloading the page.

Information and links

Two sections follow the applications. The first leads to the pages of SPPAS itself: About, how to cite the software, the Journal, and the form to send a feedback. The second gathers seven links to the web: the site, the book, the tutorials, the frequently asked questions, the source code, the resources and an award. Each of these links carries a color of its own, which does not change with the theme.

What the page asks

The licence

At the very first opening, the page asks for the licence to be agreed. Nothing else is shown until then. The answer is kept: the question is not asked again.

The Journal

The Journal lives in a tab of its own, where SPPAS writes what it did and why. When that tab is closed, the Dashboard says so and offers to open it again. The message appears and disappears on its own, the page being polled regularly.

The menu

The menu on the left is built by each application for itself. Four items are found in all of them: the button switching the CSS theme, the two accessibility buttons -- contrast, and light or dark colors -- and the button pinning the menu open.

The Dashboard adds four of its own: the Dashboard button, which reloads the page here; the Help button, opening this document; the Journal; and the button leaving SPPAS. Leaving closes the session: the server stops, and the pages still open say so.

Developer manual

Organisation

The application lives in sppas/ui/swapp/app_dashboard/. It follows the MVC pattern shared by every application of the swapp package.

  • app_dashboard.py -- DashboardWebData, which parses the JSON configuration and answers which page it can bake.
  • dashboardmaker.py -- DashboardResponseRecipe, the bakery of index.html: it receives the events and decides whether the page is created again.
  • dashboard_controller.py -- DashboardController, which holds the answers to the events and fills the view from the model.
  • dashboard_view.py -- DashboardView, which builds the HTML tree and nothing else.
  • nodes/ -- the cards of the applications, the buttons of the links, and the dialogs.

What the page is made of

The registries

The cards are not written in the page: they come from two registries. The applications are declared in WEB_APPLICATIONS, the pages in WEB_PAGES, as a list of WebPageInfo(recipe, show). A page declared with show=True gets its link in the section of information. A spin-off adds its own entries through SWAPP_PAGES.

The menu is never fed from a registry: its list is fixed. The Dashboard is where the whole set is shown, the menu is where the daily loop is.

The nodes

AppsNode.create_app_card() builds a card: an article holding the picture, the title, the description and the launching button. The links of the two other sections are built by LinksNode and AboutsNode: an a element carrying the classes card and link-button -- a link, not a button, since it leads somewhere instead of doing something.

The events

_process_events() of the recipe answers four of them, and returns whether the whole page must be created again.

  • workspace_name -- the periodic request of the JavaScript. It returns the name of the workspace, the path of its file and whether the Journal tab is alive. The page is not baked again: the browser updates what changed.
  • handle_licence_agreement -- the licence is agreed, the page is built again without the dialog.
  • handle_start_sppas -- the wx interface is launched. The answer is the error, if any, or the state saying it started.
  • event_bake=close -- leaving SPPAS. The page answers 410, Gone.

The accessibility parameters of Whakerexa never reach this method: the base recipe removes every wexa_ parameter, and the name of the CSS theme with them. Both belong to the client alone.

The stylesheets

Four sheets are loaded, in this order.

  • main_swapp.css -- the shape of every page: sizes, spacings, the side menu, the cards. No color is written there.
  • main_swapp_identity.css -- what identifies SPPAS whatever the theme: the reading font, and the colors naming a destination, a status or a step. It is never swapped.
  • main_swapp_theme.css -- the theme, carrying the id wexa-theme: the ThemeManager of Whakerexa swaps its href to change the look of the page. It is the default theme, named swapp.
  • app_dashboard.css -- what belongs to this page alone: the panel of the applications and the seven links.

The scripts

dashboard_manager.js attaches what the page needs: the click on a card of an application, the periodic request refreshing the workspace and the Journal dialog, and the buttons of the dialogs. The links towards the internal pages are not handled there: they are a elements, followed by goToLink() of Whakerexa, which carries the accessibility parameters over to the page.
